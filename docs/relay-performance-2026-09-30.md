# Relay 性能实测与优化方案

日期：2026-09-30（Asia/Shanghai）

结论：保留端到端加密。先解决大文件阻塞交互、重复传输和 Base64 解码，再升级二进制协议；公网带宽决定大文件速度的上限。当前没有证据支持把关闭加密或升级服务器 CPU 作为主要方案。

## 测试范围与方法

- 使用当前 Mac、本地 Daemon、实际阿里云 `px.mushayu.com` 和现有 v3 协议。没有关闭加密、修改生产配置或触发 Agent 执行。
- 真实接口：健康检查、工作区、长会话 Timeline、Turn 列表；真实约 6.7 MiB MP4 的 Range 请求。
- 5 次新连接握手；接口多次测量；视频 1 MiB 分段 3 次、完整文件 2 次；并发下载与小请求；同连接与独立连接对照。
- Chromium 页面冷启动共 8 次：本地/公网、桌面/390px 手机布局、正常/4 倍 CPU 降速，各组合 2 次。
- 浏览器微基准：256 KiB 随机二进制，预热后 5 组，每组 16 次，报告组中位数。使用项目真实 SessionCipher 与解码函数；候选实现只在临时测试中运行。
- 压缩另做交替顺序对照，每个接口、每种模式各 8 次，减少分时测量的网络波动偏差。
- 全部记录只保存耗时、字节数、摘要和事件类型，不保存配对信息、密钥或会话正文。

限制：这是当前网络的一次测试窗口，不是多地、多运营商统计；4 倍 CPU 降速不是实机 iPhone/Android。页面每组仅 2 次，使用区间，不宣称可靠 P95。没有测上传峰值，也没有在生产中发起真实任务来测实时 token 延迟；实时事件与取消被大文件阻塞的风险来自共用连接的实现及小请求对照。视频播放流程沿用此前已经通过的本地/Relay 大视频、进度跳转和手机旋转回归，本轮主要测传输性能。

## 实测结果

### 1. 公网大文件受线路吞吐限制，加密不是主要耗时

| 项目 | 结果 |
|---|---|
| 新建 Relay 加密连接 | 5 次中位数约 1.07 秒 |
| 空闲连接健康请求，交替对照 | 压缩约 46 ms；不压缩约 41 ms |
| 本地约 67 KB Turn 列表 | 约 1 ms |
| Relay 同一 Turn 列表 | 压缩约 57 ms；不压缩约 93 ms |
| Relay 完整 6.7 MiB 视频 | 两次约 23 秒 |
| 视频对应加密业务帧体积 | 约 9.34 MB，原文件约 6.99 MB |
| 完整视频客户端解密累计耗时 | 约 0.3 秒（Node 测量，非手机） |
| 公网直接下载现有约 2 MB 静态 JS | 三次 3.92 / 4.93 / 4.90 秒，约 0.40–0.50 MiB/s |
| Relay 1 MiB 视频分段 | 4.05–15.81 秒，波动明显 |

本地与 Relay 下载的同尺寸视频内容 SHA-256 一致。加密仅给单帧增加少量字节，主要体积膨胀来自 Base64；256 KiB 原始数据包装后约 350 KB。

静态文件下载绕开端到端加密，也出现相近的有效线路吞吐，因此应检查阿里云出口规格、用户网络和同时使用情况。不能仅凭本次测量断言购买的是某一档带宽。服务器采样 CPU 空闲约 98–99%，Relay 内存为几十 MB；采样时没有持续换页、接口丢包证据，不支持优先加 CPU。

初次顺序测试中 gzip 请求比无 gzip 慢，但受网络时段影响。交替对照确认：较大文本压缩有效，不能根据那组顺序数据关闭全部压缩。

### 2. 大文件会阻塞同一条连接上的交互

实际公网下载 2 MiB，同时发 6 次健康请求：

| 方式 | 文件耗时 | 小请求延迟 |
|---|---:|---|
| 共用一条连接 | 6.08 秒 | 1 次 198 ms，其余约 5.23–5.83 秒 |
| 文件与控制使用不同连接 | 6.42 秒 | 约 39–470 ms |

更早的 6.7 MiB 并发样本出现单次小请求等待约 22.9 秒。该值属于少量样本中的极端值，不作为稳定分位数。

同一 WebSocket 有序发送、发送队列及网络缓冲会使小响应排在大文件数据之后。“取消消息不经过应用层等待”也不能让它越过已经入队的字节。只增加应用层优先级无法完全解决。

### 3. 浏览器 Base64 解码存在明确性能问题

256 KiB 原始数据，对照结果：

| 接收处理 | 正常 CPU | 4 倍 CPU 降速 |
|---|---:|---:|
| 当前完整接收：解密、两层 JSON、Base64 | 14.07 ms | 58.17 ms |
| 仅改 Base64 解码为普通循环，其余保持 | 3.74 ms | 15.90 ms |
| Base64 当前 `Uint8Array.from` 解码 | 10.56 ms | 44.86 ms |
| Base64 普通循环解码 | 0.50 ms | 2.10 ms |
| Base64 浏览器原生解码 | 0.056 ms | 0.238 ms |
| NaCl 直接二进制解密 | 2.09 ms | 8.79 ms |
| WebCrypto AES-GCM 直接二进制解密 | 1.09 ms | 4.63 ms |

仅替换解码方式，完整接收 CPU 时间下降约 73%，不需要改协议。原生 Base64 API 应做能力检测，旧浏览器回退到普通循环。

这不是公网下载速度提升 73%：当前公网主要受带宽限制。收益是降低浏览器 CPU、减少手机卡顿，并为更快网络释放吞吐空间。此前 Node 原生 AES-GCM 的极高吞吐不能直接套到浏览器；本次浏览器结果用于方案排序。

### 4. 首屏及会话初始化存在重复数据与等待

真实长会话的一次采样：

- 初始 Timeline 30 条：约 15.7 KB，gzip 后约 3.6 KB。
- Turn 列表：约 67 KB，gzip 后约 10.2 KB。
- 获取当前 Timeline 后，带当前游标订阅 SSE，仍收到 `timeline-synced` 约 67.1 KB，以及约 6.2 KB control。这些初始化内容不走 gzip。
- 前端此前已经单独请求 turns 和 control；初始化订阅因此重复传输了大批数据。
- 工作台初始化先请求 projects/providers，再按每个工作区请求 tasks，并等待全部完成才显示列表，是额外往返和请求数来源。

真实页面冷启动采样：

| 场景 | 会话列表可见 | 点击长会话后内容可见 |
|---|---:|---:|
| 本地桌面 | 150–206 ms | 117–352 ms |
| 公网桌面 | 1.39–2.12 秒 | 349 ms–2.38 秒 |
| 本地手机布局 + 4 倍 CPU 降速 | 434–442 ms | 231–252 ms |
| 公网手机布局 + 4 倍 CPU 降速 | 1.74–2.77 秒 | 957 ms–1.43 秒 |

不同源都是新浏览器上下文，冷缓存；端点数据在测试期间可能随会话变化。表格用于识别量级，不作精确优化比例承诺。

### 5. 视频先等待完整分段；静态资源缓存可改善

- 当前每个视频 Range 最多 1 MiB，页面 `arrayBuffer()` 收完后才交给 Service Worker，首字节已到达也不能马上供播放器消费。
- 网络慢时 1 MiB 等待会放大起播和拖动延迟。增大分段并非当前网络下的最优解。
- 公网静态 JS 已有 gzip，无需重复引入；带哈希的 JS 当前 `Cache-Control: public, max-age=0`，可改长期 immutable 缓存，降低二次访问重新验证成本。首页和 Service Worker 应保留更新检查，不能一并永久缓存。

## 推荐实施顺序

### 第一批：保持 v3，加速交互与首屏

1. **优化 Base64 实现**：有原生 `Uint8Array.fromBase64` 时使用；否则普通循环回退。同步检查上传编码；保留输入校验和现有加密。
2. **独立控制和媒体连接**：会话 API、SSE、取消继续使用控制连接；视频/音频及大文件按需启用一条额外连接。两条都执行完整配对和端到端加密。媒体连接空闲后回收；并发流数有上限。
   - 先隔离大文件，必要时再将大量正文与交互分级。
   - 当前服务器按连接计数，需要同步核对每用户连接配额；不能无上限按每个请求新建连接。
3. **消除重复初始化数据**：请求得到 turns/control 后，SSE 初次订阅不再无条件发送同样的全量数据。
   - 不能简单设置 `snapshot=false`：必须保留从游标之后的事件补发和 epoch 变化时的 reset。
   - 为 turns/control 加版本或增量更新；正常重连按游标补缺口，真正不一致时才获取快照。
4. **合并工作台初始化请求**：返回 projects + 会话摘要，避免 N 个工作区请求后才呈现；Provider 探测不挡住已有会话显示。
   - 保留工作区与会话数据边界，大规模列表需分页/渐进加载，避免变成无限增长的全量接口。
5. **压缩阈值和静态缓存**：较大文本保留 gzip，已知很小的响应跳过压缩；带哈希静态资源长期缓存，首页及 SW 正常更新。

收益：针对目前实测瓶颈，成本和风险比最高。无需关闭加密或强制更换全部客户端协议。

### 第二批：新版本二进制业务帧，减少带宽和解析

1. 请求/响应正文使用二进制帧，帧头携带 requestId、类型、序号；控制元数据仍可使用 JSON。
2. 去掉正文 Base64 和重复 JSON。对于视频等未压缩二进制，预计总传输字节比当前少约 25%（消除 33% 的膨胀）。网络受限时具有明确收益，但实际耗时仍取决于链路及调度。
3. 首版可保留当前 NaCl 算法，避免把传输格式和加密实现同时更换，缩小评审范围。
4. 协议能力须绑定到认证握手，客户端与 Daemon 协商一致；保留 v3 兼容/明确升级提示，不允许静默取消认证或加密。
5. 补充接收端流量反馈与有界缓冲。当前超过 4 MiB 接收队列会取消，应演进为可控暂停/恢复，不能通过无限增大缓存处理慢手机。

### 第三批：视频流式交付与端侧优化，按第二批复测决定

- Service Worker 收到首批媒体字节后即可交给播放器，保持正确 HTTP Range、Content-Length、取消和超时语义；断流时能重试。
- 首段可对照测试 128/256 KiB，播放稳定后再自适应至 512 KiB/1 MiB。预读最多一个窗口，优先服务用户 seek，关闭及时取消。
- 小段会增加往返，大段会延迟起播，因此必须测完播连续性、起播和 seek，不能只看下载峰值。
- 若二进制协议之后手机 CPU 仍是瓶颈，再选择 Web Worker 或 WebCrypto AES-GCM。异步加密必须保持帧顺序、方向密钥隔离、唯一 nonce、重放检测和有界并发。
- 原生 AES-GCM有收益，但当前优先级低于移除 Base64 和隔离媒体连接，不建议作为第一步重构。

### 配套：验证阿里云带宽后按需升级

- 当前静态文件与 Relay 的实际线路吞吐都偏低。先核对购买带宽/流量规格和不同时段测量；确认出口上限后，升级带宽会比升级 CPU 更直接。
- 静态前端可独立缓存/CDN，降低页面加载对 Relay 出口的竞争；CDN只承载公开静态资源，业务保持现有加密链路。
- 独立连接可以降低排队，不能创造额外总带宽。多朋友同时下载仍须总量限制和公平调度。

## 验收与回退

以下为实施后的目标，不是本轮已实现的承诺：

- 同等网络条件下载文件时，控制请求不再出现多秒排队；目标 P95 小于 500 ms，至少做 30 次以上采样。
- v3 解码微基准在 4 倍 CPU 降速下 256 KiB 完整接收小于 20 ms，并验证实际帧尺寸分布。
- 长会话初次订阅不再重复发送相同的约 67 KB Turn 列表，重连无消息缺失/重复，运行状态及时恢复。
- 二进制媒体帧总字节较当前减少至少约 24%，下载内容摘要一致。
- 测试桌面 Chromium、Safari 与真实 iPhone/Android；加入高 RTT、低带宽、后台恢复、连接中断、并发 1/4 客户端。
- 视频测试冷起播、拖动、横竖屏、全屏、取消；音频、上传和慢消费者测试不能遗漏。
- 第一批按功能开关分步上线；第二批先客户端/Daemon 双版本兼容，灰度后切默认，不强制破坏已有配对。

## 第一批实施与复测

已实现（保持 v3 协议与端到端加密）：

- Base64 优先使用浏览器原生解码，旧浏览器用普通循环复制。
- 文件、图片、音视频正文按需共用一条独立媒体连接；原会话请求和事件仍使用控制连接。媒体响应读完、取消或失败后计数归零，空闲 30 秒回收。两条连接均认证和加密；沿用每连接最多 64 个请求及接收缓冲上限，没有按请求创建连接。每个页面最多两条连接，现有服务默认 16 客户端连接配额按连接计算，需要留意多人同时使用的容量。
- turns/control 接口返回内容版本。共享事件订阅携带已持有版本，相同时省掉正文；改变时发送新快照。仍保留游标之后的全部历史补发、分页和 epoch 重置，未使用 `snapshot=false` 替代会话同步。
- 新增 `/api/v2/workbench` 聚合工作区及会话摘要；首屏只需一次列表请求，Provider 探测并行执行。摘要范围沿用现有工作台，未加入分页，不传 Timeline 和工具详情。
- 已知长度小于 1 KiB 的响应跳过 gzip；较大文本及未知长度文本继续按已有策略压缩，SSE/视频不压缩。
- Relay 的哈希静态资源使用一年 immutable 缓存，首页和 Service Worker 使用 `no-cache` 正常检查更新。

### 真实阿里云通道复测

浏览器运行修改后的连接池，业务经过现有阿里云 Relay，由本地新 Daemon 响应。公网服务器本轮未部署，WebSocket 仍沿用通用 v3 转发。对照组使用同一份新解码实现，但共享一条连接，因此主要衡量连接隔离效果。每次文件 2 MiB，同时发六个健康请求；下载摘要全部一致。

完整复测五轮，每组 30 个小请求：

| 方式 | 下载耗时 | 小请求中位数 | 小请求 P95 | 小请求范围 |
|---|---:|---:|---:|---:|
| 共用连接 | 5.40–7.25 秒 | 5.69 秒 | 6.71 秒 | 219 ms–6.86 秒 |
| 实际新连接池 | 6.02–6.37 秒 | 72 ms | 210 ms | 35–265 ms |

P95 使用 30 个样本的 nearest-rank 值，仅代表当前单客户端、当前网络窗口。五轮下载均为同一份 2 MiB 内容且 SHA-256 相同。隔离连接显著减少小请求排队，但没有据此宣称大文件总吞吐提升。

同一长会话已通过 HTTP 获取 turns/control 后：无版本标识的初始事件为 74,563 字节；带版本后为 1,325 字节，减少约 98.2%。其中 `timeline-synced` 从 67,202 字节变为 218 字节，相同 control 不再重复发送；并非削减首次必须读取的会话数据。

256 KiB 完整接收浏览器微基准：正常 CPU 从 14.07 ms 降到 3.31 ms，4 倍 CPU 降速从 58.17 ms 降到 13.63 ms，处理时间减少约 76%。不代表公网下载提速 76%。原测试脚本的字段名仍保留旧描述，复测时该字段实际调用新的 `decodeBase64`。

新构建的页面由本地提供静态文件、业务使用真实阿里云通道。桌面列表可见 866–1,078 ms，点击长会话后内容可见 150–160 ms；手机布局加 4 倍 CPU 降速分别为 858–1,259 ms 和 363–406 ms，每组仅两次。这组排除了公网静态文件下载，不能直接与先前公网冷启动整页数据比较。线上静态缓存需要部署后再测，Safari/真实手机、不同网络、多用户仍需后续验证。

## 二进制与视频流式优化完成

### 实施范围

- 在原 v3 加密握手中协商 `binary-v1` 正文能力，保持现有配对链接与公网盲转发协议。协商内容纳入会话密钥派生；新客户端连接旧 Daemon、新 Daemon 接受旧客户端都回退到原格式，仍执行认证和加密。
- 上传与响应正文改为带请求标识的二进制帧，省去 Base64 与两层 JSON。控制帧继续 JSON。控制与正文共用严格递增的认证会话序号，拒绝重放、乱序、篡改与错误方向的正文帧。
- 为新格式加入每个响应 512 KiB 接收额度，页面消费后通过加密控制帧归还额度。慢消费者使 Daemon 暂停读取与发送，取消/断线/请求超时会释放等待者；未通过扩大无限缓冲解决慢手机。旧格式仍沿用原缓冲限制。
- 视频桥接改为 `Response` 流：响应头和首批数据到达即可供浏览器读取，Service Worker 每次按需求拉取一块并转移 ArrayBuffer。取消与错误沿页面、加密连接传至 Daemon。Worker 用请求生命周期等待保持流式桥接，并保留旧页面整段响应兼容。
- 视频起播和非连续 seek 使用 256 KiB Range；连续读取逐步增至 512 KiB/1 MiB，每次最多 1 MiB，HEAD、尾段和 416 行为保留。
- 手机浏览器限制自动播放时，元数据就绪即显示原生控件，允许手动播放，不再等待首帧事件而一直隐藏播放器。
- 远程工作台在后台预热播放器 Worker；已有同脚本的激活 Worker 立即复用，后台更新检查不阻塞播放。首次注册期限从 15 秒调到 45 秒，页面接管和通信分别保留 15 秒期限并区分错误阶段。
- 保留 NaCl，未引入 WebCrypto 或解密 Worker：二进制复测已达到端侧处理目标，不同时扩大加密算法和并发重构范围。

### 阿里云通道对照

同一浏览器、真实公网链路、同一 2 MiB 视频，原格式与二进制交替顺序各测三次。两组均采用已优化的解码实现，因此下面是二进制格式的额外收益。

| 指标 | 原 JSON/Base64 正文 | 二进制正文 |
|---|---:|---:|
| 响应密文字节，不含 WebSocket/TLS 头 | 2,800,642–2,801,290 | 2,099,551 |
| 下载耗时 | 5.84–6.74 秒 | 4.90–4.98 秒 |
| 三次耗时中位数 | 6.66 秒 | 4.97 秒 |
| 全部下载 SHA-256 | 一致 | 一致 |

响应字节减少约 25.0%；本窗口下载中位数减少约 25.4%。样本仅三次，不作稳定 P95 或跨网络承诺。

256 KiB 完整接收微基准：新解码的 JSON/Base64 正文为 3.20 ms，二进制为 2.09 ms；4 倍 CPU 降速为 13.53 ms 与 9.00 ms。相较最初 58.17 ms 的手机降速基线，最终处理耗时减少约 84.5%，不等于网络速度提升这一比例。
